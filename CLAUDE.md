# CLAUDE.md — воркспейс фич qgames

Этот каталог — рабочее место для фич, которые затрагивают оба репозитория. Основная сессия — **сеньор-фулстек**: сама анализирует, пишет код в обоих репозиториях и прогоняет проверки. Ревью делает отдельный агент `reviewer`. Решения принимает пользователь.

| Репозиторий | Путь | Правила |
|---|---|---|
| Архитектура системы | `adr/` (этот репозиторий) | `adr/README.md`: индекс ADR, диаграмм C4 и ERD, правила ведения |
| Скрипты VPS | `server/` (этот репозиторий) | `deploy.sh` (→ `/opt/qgames/bin/`), хук certbot (→ `/etc/letsencrypt/renewal-hooks/deploy/qgames.sh`). Исходник — здесь; после правки залить на сервер (`ssh qgames`), устройство — `adr/system/hosting.md`, `adr/security/server-hardening.md` |
| Бэкенд | `../qgames-backend-monorepo` | корневой `CLAUDE.md` (ядро) + вложенные `CLAUDE.md` областей (рядом с кодом, по ссылкам из ядра) |
| Фронтенд | `../qgames-frontend-monorepo` | корневой `CLAUDE.md` (ядро) + вложенные `CLAUDE.md` областей (рядом с кодом, по ссылкам из ядра) |

**Где что лежит.** `adr/` — «почему» (ADR с отвергнутыми вариантами) и «что и как связано» (C4, ERD) для всей системы. Это описание для человека и контекст для анализа. `CLAUDE.md` репозиториев (корневые и вложенные) — «как писать код», со ссылками на `adr/`.

**Раскладка:** все три репозитория лежат рядом в одной родительской папке с фиксированными именами (`qgames-workspace`, `qgames-backend-monorepo`, `qgames-frontend-monorepo`). Пути во всех файлах воркспейса — относительно его корня (рабочего каталога сессии); абсолютные пути не пишем.

## Роли

- **Фулстек (основная сессия)** — анализ, вопросы пользователю, код в обоих репозиториях, проверки, итог. Только он общается с пользователем.
- **`reviewer`** — read-only ревью обоих репозиториев, запускается после реализации.

Правило «репозиторий бэкенда не правим» из CLAUDE.md фронтенда (и обратное — для бэкенда) относится к сессиям, открытым в одном репозитории. В этом воркспейсе пользователь поручает основной сессии обе стороны фичи.

## Главные правила

- **Решения принимает пользователь.** Архитектурные развилки (по §0 обоих CLAUDE.md), контракт API и вопросы ревьюера показываются пользователю через `AskUserQuestion`: варианты + рекомендация. Сам за пользователя не решаешь.
- **Проблемы не замалчиваются.** Риски, техдолг и расхождения, найденные по ходу работы или ревьюером, доходят до пользователя.
- **Без версионирования игр и совместимости со старыми данными.** Сущность игры не версионируется (неоправданно дорого). Меняя игры, их состояние, события и логи партий, о старых данных не думаем: прода нет, после запуска такие случаи мигрируются вручную. Версии, слои совместимости и миграции старых данных не предлагаем.
- **Git:** никто не коммитит и не пушит. Коммиты в обоих репозиториях делает пользователь.
- Правила обоих CLAUDE.md важнее этого файла по части кода; при противоречии — вопрос пользователю.

## Экономия контекста

- **Правила читаются по мере надобности.** Ядро `CLAUDE.md` репозитория читается, когда начинается работа в нём; вложенные `CLAUDE.md` — только те, на которые ядро ссылается для затронутой области. Если фича касается одной стороны, правила другой не читаются.
- **`adr/` читается через индекс:** `adr/README.md`, затем только нужные диаграммы и ADR, целиком папка не читается.
- **Код ищется точечно:** `Grep`/`Glob` и `Read` нужного диапазона строк, а не файлы целиком. `Explore` — только когда объём поиска неясен.
- **`BACKLOG.md` не читается целиком:** нужная задача ищется через `Grep`.
- **Вывод сборок не тащится в контекст целиком:** `./gradlew build --quiet` (при падении — хвост вывода и отчёт упавшего теста), у `pnpm` — только ошибки.

## Процесс задачи

Любая задача, которую пользователь описал в сессии, идёт по этому процессу. Объём процесса — по размеру задачи: для мелкой правки шаги 2 и 5 могут быть короткими, но контракт API и развилки всё равно утверждает пользователь.

1. **Анализ.** Прочитать `adr/README.md`, затем нужные диаграммы C4/ERD и ADR затронутой области, ядро CLAUDE.md затронутых репозиториев, нужные вложенные `CLAUDE.md` и места кода. Предлагаемая архитектурная альтернатива сверяется с «Рассмотренными вариантами» ADR.
2. **Решения пользователя.** Все развилки и контракт (ручки API — группы `portal` и `admin`, DTO, `required`/nullable, коды ошибок) → `AskUserQuestion`. Без утверждения контракта дальше не идти.
   - **Спецификация `features/<yyyy-MM-dd>-<фича>.md`** (шаблон ниже) пишется, только если меняется контракт API или фича большая. Она нужна ревьюеру и как точка восстановления после сжатия контекста. Мелкие задачи (только UI, только бэкенд без контракта, задачи из BACKLOG) делаются без неё; решения тогда фиксируются в чате и передаются ревьюеру в промпте.
3. **Бэкенд.** Реализация по правилам бэкенда, `./gradlew build`. Если менялся контракт — поднять стенд (`docker compose up --build -d --wait` в репозитории бэкенда), чтобы были доступны `/v3/api-docs/portal` и `/v3/api-docs/admin`.
4. **Фронтенд.** Если контракт менялся — `pnpm api:fetch` и `pnpm api:generate`, проверить дифф `packages/api/src/generated/`. Затем UI по правилам фронтенда, `pnpm typecheck` и `pnpm lint`.
5. **Ревью.** Запустить `reviewer`, передать путь к спецификации или (без неё) цель, контракт и решения. Из ответа:
   - `## Замечания` — исправить самому, затем повторное ревью **тем же** `reviewer` через `SendMessage`, только по исправленным местам;
   - `## Вопросы пользователю` → `AskUserQuestion`, ответ — в спецификацию (если есть).
   - После 2 кругов без сходимости — остановиться и показать пользователю, что не сходится.
   - Пользователь может сказать «без ревью» — тогда шаг пропускается.
6. **Актуализировать `adr/` и дать итог пользователю.** Перед итогом обновить всё, что изменение затронуло: диаграммы C4 (новый или изменённый компонент, связь, поток, маршрут), ERD (DDL-миграции), ADR (принятое решение, новый отвергнутый вариант, закрытый открытый вопрос), индекс `adr/README.md`. Итог: что сделано в каждом репозитории (файлы, проверки и их результат), что обновлено в `adr/`, принятые решения, открытые вопросы. Новое правило написания кода — предложить формулировку для ядра CLAUDE.md или нужного вложенного `CLAUDE.md`, внести после согласия. Обоснование решения пишется в ADR, а не в CLAUDE.md.
7. **Удалить спецификацию.** Спецификация — рабочий файл на время фичи, журнал реализованных фич не ведём. До удаления переносится всё, что должно остаться: решения — в ADR (`adr/`), правила кода — в CLAUDE.md репозиториев (корневые или вложенные), техдолг и задачи на доработку — в `BACKLOG.md` воркспейса понятным языком («что не так → чем грозит → как поправить», где искать). Папка `features/` в `.gitignore`.
8. **Задачи из `BACKLOG.md`** берутся в работу как обычные фичи; выполненная задача удаляется из файла.

## Как вести `adr/`

- **Живые ADR без номеров:** имя файла — slug предмета решения, дат и статусов нет. ADR лежит в папке своей группы: `system/`, `backend/`, `game/`, `contract/`, `security/`, `frontend/` (`adr/game/realtime-transport.md`), группа в индексе совпадает с папкой. Если решение меняется, ADR переписывается на месте, прежний вариант уходит в «Рассмотренные варианты» с причиной. Если от решения отказались, ADR удаляется. Новый ADR пишется по `adr/template.md` и добавляется в индекс `adr/README.md`.
- **C4** — Mermaid (`C4Context`, `C4Container`, `C4Component`, `C4Deployment`; динамика — `sequenceDiagram`). Рядом с диаграммой — таблица элементов или разделы с кратким устройством (текст читается без рендера). Файл C4 может быть и без диаграммы, если область — это детали устройства (`3-backend-auth.md`). **ERD** — Mermaid `erDiagram` по модулю-владельцу, источник правды — DDL-миграции (CREATE и последующие ALTER).
- **Размер:** ADR ≤ ~60 строк, файл C4 ≤ ~120, ERD ≤ ~100, README ≤ ~80. Если файл растёт, он делится.
- В ADR попадают только решения, согласованные с пользователем. Код в `adr/` не дублируется: пути к коду пишутся с префиксом `backend/` или `frontend/`.
- После правки диаграмм проверить, что они рендерятся (Mermaid в браузере через Playwright MCP).
