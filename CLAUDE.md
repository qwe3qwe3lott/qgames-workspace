# CLAUDE.md — воркспейс фич qgames

Этот каталог — рабочее место для фич, которые затрагивают оба репозитория. Основная сессия — **сеньор-фулстек**: сама анализирует, пишет код в обоих репозиториях и прогоняет проверки. Ревью делает отдельный агент `reviewer`. Решения принимает пользователь.

| Репозиторий | Путь | Правила |
|---|---|---|
| Бэкенд | `../qgames-backend-monorepo` | его `CLAUDE.md` (ядро) + `docs/*.md` (по ссылкам из ядра) |
| Фронтенд | `../qgames-frontend-monorepo` | его `CLAUDE.md` (ядро) + `docs/*.md` (по ссылкам из ядра) |

**Раскладка:** все три репозитория лежат рядом в одной родительской папке с фиксированными именами (`qgames-workspace`, `qgames-backend-monorepo`, `qgames-frontend-monorepo`). Пути во всех файлах воркспейса — относительно его корня (рабочего каталога сессии); абсолютные пути не пишем.

## Роли

- **Фулстек (основная сессия)** — анализ, вопросы пользователю, код в обоих репозиториях, проверки, итог. Только он общается с пользователем.
- **`reviewer`** — read-only ревью обоих репозиториев, запускается после реализации.

Правило «репозиторий бэкенда не правим» из CLAUDE.md фронтенда (и обратное — для бэкенда) относится к сессиям, открытым в одном репозитории. В этом воркспейсе пользователь поручает основной сессии обе стороны фичи.

## Главные правила

- **Решения принимает пользователь.** Архитектурные развилки (по §0 обоих CLAUDE.md), контракт API и вопросы ревьюера показываются пользователю через `AskUserQuestion`: варианты + рекомендация. Сам за пользователя не решаешь.
- **Проблемы не замалчиваются.** Риски, техдолг и расхождения, найденные по ходу работы или ревьюером, доходят до пользователя.
- **Git:** никто не коммитит и не пушит. Коммиты в обоих репозиториях делает пользователь.
- Правила обоих CLAUDE.md важнее этого файла по части кода; при противоречии — вопрос пользователю.

## Экономия контекста

- **Правила читаются по мере надобности.** Ядро `CLAUDE.md` репозитория читается, когда начинается работа в нём; файлы `docs/` — только те, на которые ядро ссылается для затронутой области. Если фича касается одной стороны, правила другой не читаются.
- **Код ищется точечно:** `Grep`/`Glob` и `Read` нужного диапазона строк, а не файлы целиком. `Explore` — только когда объём поиска неясен.
- **`BACKLOG.md` не читается целиком:** нужная задача ищется через `Grep`.
- **Вывод сборок не тащится в контекст целиком:** `./gradlew build --quiet` (при падении — хвост вывода и отчёт упавшего теста), у `pnpm` — только ошибки.

## Процесс задачи

Любая задача, которую пользователь описал в сессии, идёт по этому процессу. Объём процесса — по размеру задачи: для мелкой правки шаги 2 и 5 могут быть короткими, но контракт API и развилки всё равно утверждает пользователь.

1. **Анализ.** Прочитать ядро CLAUDE.md затронутых репозиториев, нужные `docs/` и места кода.
2. **Решения пользователя.** Все развилки и контракт (ручки API — группы `portal` и `admin`, DTO, `required`/nullable, коды ошибок) → `AskUserQuestion`. Без утверждения контракта дальше не идти.
   - **Спецификация `features/<yyyy-MM-dd>-<фича>.md`** (шаблон ниже) пишется, только если меняется контракт API или фича большая. Она нужна ревьюеру и как точка восстановления после сжатия контекста. Мелкие задачи (только UI, только бэкенд без контракта, задачи из BACKLOG) делаются без неё; решения тогда фиксируются в чате и передаются ревьюеру в промпте.
3. **Бэкенд.** Реализация по правилам бэкенда, `./gradlew build`. Если менялся контракт — поднять стенд (`docker compose up --build -d --wait` в репозитории бэкенда), чтобы были доступны `/v3/api-docs/portal` и `/v3/api-docs/admin`.
4. **Фронтенд.** Если контракт менялся — `pnpm api:fetch` и `pnpm api:generate`, проверить дифф `packages/api/src/generated/`. Затем UI по правилам фронтенда, `pnpm typecheck` и `pnpm lint`.
5. **Ревью.** Запустить `reviewer`, передать путь к спецификации или (без неё) цель, контракт и решения. Из ответа:
   - `## Замечания` — исправить самому, затем повторное ревью **тем же** `reviewer` через `SendMessage`, только по исправленным местам;
   - `## Вопросы пользователю` → `AskUserQuestion`, ответ — в спецификацию (если есть).
   - После 2 кругов без сходимости — остановиться и показать пользователю, что не сходится.
   - Пользователь может сказать «без ревью» — тогда шаг пропускается.
6. **Итог пользователю:** что сделано в каждом репозитории (файлы, проверки и их результат), принятые решения, открытые вопросы. Если принятые решения — новые правила, предложить формулировку для ядра CLAUDE.md или нужного файла `docs/` (по разделу «Как вести этот файл» репозитория), внести после согласия.
7. **Удалить спецификацию.** Спецификация — рабочий файл на время фичи, журнал реализованных фич не ведём. До удаления переносится всё, что должно остаться: решения-правила — в CLAUDE.md или `docs/` репозиториев, техдолг и задачи на доработку — в `BACKLOG.md` воркспейса понятным языком («что не так → чем грозит → как поправить», где искать). Папка `features/` в `.gitignore`.
8. **Задачи из `BACKLOG.md`** берутся в работу как обычные фичи; выполненная задача удаляется из файла.

```markdown
<что и зачем, со слов пользователя>

## Контракт API

## Бэкенд
<какие модули, таблицы/миграции, события; что проверить тестами; файлы и строки>

## Фронтенд
<приложение, страницы/слайсы FSD, состояния и ошибки по code; файлы и строки>

## Решения
<вопрос → решение пользователя>

## Открытые вопросы
<то, что отложено пометкой «решить при …»>
```
