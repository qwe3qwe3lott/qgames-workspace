# Отделение админки

Область: backend, frontend · Диаграммы: [c4/2-containers](../c4/2-containers.md), [c4/3-backend-auth](../c4/3-backend-auth.md), [erd/admin-auth](../erd/admin-auth.md) · Код: `backend/admin-auth`, `frontend/apps/admin`

## Контекст

У администраторов другие полномочия и другой риск компрометации. Сессия админа не должна давать доступ к порталу и наоборот. При этом приложение бэкенда одно.

## Решение

- Отдельный модуль **`admin-auth`** — упрощённая копия user-auth (без регистрации, Google и событий): свои таблицы, ключ подписи, issuer, короткие сессии (access 5 мин, refresh 15 мин скользящий).
- Отдельная **группа API `admin`** (`/api/admin/**`) и своя цепочка Security. Отдельный SPA `apps/admin` на поддомене `admin.<домен>` ходит только в эту группу.
- Куки названы иначе, чем у портала (`admin_*`, пути под `/api/admin`), поэтому они не перетирают друг друга.
- Ролей нет, все админы равны. Первого админа создаёт бутстрап из env, если таблица пуста.

## Рассмотренные варианты

| Вариант | Почему нет |
|---|---|
| Админка через ручки портала (общая группа API и куки) | Решение пользователя: у администраторов отдельные ручки, сессия и ключи JWT |

## Последствия

- Код admin-auth частично дублирует user-auth (BACKLOG «Дублирование admin-* и user-*»).
- nginx на хосте портала закрывает `/api/admin/**` (404), на хосте админки — остальные `/api/**`.
