# Токены доступа и обновление сессии

Область: backend, frontend · Диаграммы: [c4/3-backend-auth](../c4/3-backend-auth.md), [c4/dynamic/auth](../c4/dynamic/auth.md), [erd/user-auth](../erd/user-auth.md) · Код: `TokenService`, `RefreshTokenRepository`, `SecurityConfig`, `frontend/packages/api` (mutator)

## Контекст

API должен проверять пользователя без похода в БД на каждый запрос. Утечка refresh-токена должна обнаруживаться. Параллельные вкладки обновляют сессию одной кукой одновременно.

## Решение

- **Access — JWT ES256** с коротким TTL (игроки 15 мин, админы 5 мин). Проверка локальная, по публичному ключу из конфигурации. У игроков и админов разные ключи и issuer.
- **Refresh — случайная строка**, в БД хранится только SHA-256. Ротация при каждом обновлении, семья по `family_id`. Повтор ротированного токена позже окна отзывает всю семью (`REFRESH_TOKEN_REUSED`).
- **Окно терпимости 10 с:** повтор ротированного токена в окне (если в семье есть активный) выдаёт ещё одну пару той же сессии.
- Фронт делает **один общий (single-flight) refresh** на 401 `UNAUTHENTICATED` и повторяет запрос один раз.
- Ключи приходят из конфигурации или секретов и при старте не генерируются.

## Рассмотренные варианты

| Вариант | Почему нет |
|---|---|
| HMAC-подпись JWT | Секрет проверки совпадает с секретом подписи: проверяющий может выпускать токены; сложнее ротация |
| Строгая ротация refresh без окна терпимости | Параллельные вкладки, обновляющие сессию одной кукой, разлогинивают пользователя |
| Принимать повтор ротированного токена после окна, пока преемник не использован (с отзывом преемника, срок 1 ч) | Ещё одно окно и ветка в `rotate` усложняют систему ради редкого случая (решение пользователя) |
| Только поднять окно терпимости | Покрывает лишь быстрые повторы, а окно шире ослабляет обнаружение кражи |

## Последствия

- Отзыв access-токена действует только после истечения TTL.
- **Принятый риск — потерянный ответ refresh.** Если сервер ротировал токен, а ответ с новой кукой до браузера не дошёл (обрыв сети), у клиента остаётся неверный токен. Его повтор после окна отзывает сессию, и пользователь входит заново. Частный случай — refresh из выгружаемой страницы — фронт не допускает (`frontend/apps/portal/src/shared/lib/sse/createEventStream.ts`).
