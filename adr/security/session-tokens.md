# Хранение сессии и защита от межсайтовых запросов

Область: backend, frontend · Диаграммы: [c4/2-containers](../c4/2-containers.md), [c4/3-backend-auth](../c4/3-backend-auth.md) · Код: `AuthCookies`, `SecurityConfig`, `frontend/docker/nginx`, `rsbuild` `server.proxy`

## Контекст

Токены сессии нельзя отдавать JavaScript (XSS). Два фронта (портал и админка) ходят в одно приложение. Хочется обойтись без CORS и без CSRF-токенов.

## Решение

- **Токены — только в HttpOnly-куках** (`HttpOnly; Secure; SameSite=Lax`, host-only), в теле ответов их нет. Фронт токены не видит и не хранит.
- **Same-origin через reverse proxy:** каждый фронт ходит в API своего хоста (`<домен>/api/**`, `admin.<домен>/api/admin/**`). **CORS нет:** в обеих цепочках он выключен, заголовков `Access-Control-*` нет.
- **CSRF-токенов нет.** Защиту дают три вещи: `SameSite=Lax` (куки не уходят с кросс-сайтовых POST/PUT/PATCH/DELETE и `fetch`), тела только JSON (форма и `text/plain` получают 415, JSON с другого origin требует preflight) и то, что портал и админка — один сайт, а чужие сайты кук не получают (`duckdns.org` — публичный суффикс).

## Рассмотренные варианты

| Вариант | Почему нет |
|---|---|
| Фронт и API на разных сайтах | Пришлось бы ставить `SameSite=None` и вводить CSRF-токены; сторонние куки блокируются браузерами |
| CORS + отдельный API-поддомен (`api.<домен>`) | Лишние CORS-настройки и preflight на каждый запрос, списки origin в проде и локально |
| Прямые запросы фронта на api-домен (`PUBLIC_API_URL`) + CORS | Адрес в env, CSP `connect-src` на каждое окружение |

## Последствия

**Принятый риск.** Хосты портала и админки — один сайт. Со страницы админки Lax-куки портала уходят, и POST без тела (старт, пауза, отмена партии, logout) выполнится как «простой» запрос без preflight. Так же поток комнаты (GET, который «входит» в комнату) можно открыть переходом верхнего уровня с любого сайта или через `EventSource` с хоста админки. Опасно только при XSS в админке, данные чужой странице недоступны.

Перенос фронта на другой сайт (не поддомен) требует пересмотреть модель CSRF.

## Открытые вопросы

- Решить при деплое: проверка `Sec-Fetch-Site`/`Sec-Fetch-Mode` на изменяющих ручках и SSE (BACKLOG «Защита от запросов с соседнего поддомена»).
