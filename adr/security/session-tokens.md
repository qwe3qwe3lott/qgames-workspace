# Хранение сессии и защита от межсайтовых запросов

Область: backend, frontend · Диаграммы: [c4/2-containers](../c4/2-containers.md), [c4/3-backend-auth](../c4/3-backend-auth.md) · Код: `AuthCookies`, `SecurityConfig`, `FetchMetadataFilter`, `frontend/docker/nginx`, `rsbuild` `server.proxy`

## Контекст

Токены сессии нельзя отдавать JavaScript (XSS). Два фронта (портал и админка) ходят в одно приложение. Хочется обойтись без CORS и без CSRF-токенов. Портал и `admin.<домен>` — один сайт (`duckdns.org` — публичный суффикс), поэтому Lax-куки портала уходят и со страницы админки. Подписка на поток комнаты — GET, который входит в комнату.

## Решение

- **Токены — только в HttpOnly-куках** (`HttpOnly; Secure; SameSite=Lax`, host-only), в теле ответов их нет. Фронт токены не видит и не хранит.
- **Same-origin через reverse proxy:** каждый фронт ходит в API своего хоста (`<домен>/api/**`, `admin.<домен>/api/admin/**`). **CORS нет:** в обеих цепочках он выключен, заголовков `Access-Control-*` нет.
- **CSRF-токенов нет.** Защиту дают `SameSite=Lax` (чужие сайты не получают кук на POST/PUT/PATCH/DELETE и `fetch`), тела только JSON (форма и `text/plain` получают 415, JSON с другого origin требует preflight) и проверка Fetch Metadata.
- **Fetch Metadata на `/api/**`** (`FetchMetadataFilter`, первым в обеих цепочках, до аутентификации): 403 `CROSS_SITE_REQUEST`, если `Sec-Fetch-Site` — `cross-site` или `same-site` (любой метод), либо `Sec-Fetch-Mode: navigate`. Так отсекаются POST без тела с хоста админки и вход в комнату переходом по ссылке или `EventSource` с другого хоста. Без заголовков (curl, старые браузеры) запрос пропускается. Код 403 в OpenAPI не описан: наши фронты его не получают.

## Рассмотренные варианты

| Вариант | Почему нет |
|---|---|
| Фронт и API на разных сайтах | Пришлось бы ставить `SameSite=None` и вводить CSRF-токены; сторонние куки блокируются браузерами |
| CORS + отдельный API-поддомен (`api.<домен>`) | Лишние CORS-настройки и preflight на каждый запрос, списки origin в проде и локально |
| Прямые запросы фронта на api-домен (`PUBLIC_API_URL`) + CORS | Адрес в env, CSP `connect-src` на каждое окружение |
| Fetch Metadata только на изменяющих методах и SSE-ручках | Список SSE-ручек и GET с побочным эффектом нужно поддерживать; легитимных межсайтовых запросов к `/api` всё равно нет |
| Проверка `Origin` по списку хостов | Список origin на каждое окружение; на GET-навигации браузер `Origin` не шлёт |
| Принять риск (было до фильтра) | Действия от имени игрока при XSS в админке и «заведение» игрока в чужую комнату ссылкой |

## Последствия

**Принятый риск.** Браузер без `Sec-Fetch-*` (старше 2023 года) проходит фильтр: для него остаётся прежняя модель — POST без тела с хоста админки и вход в комнату переходом по ссылке. Данные чужой странице недоступны.

API нельзя открыть в адресной строке браузера (navigate → 403); Swagger UI и `/v3/api-docs` вне `/api` и не проверяются.

Перенос фронта на другой сайт (не поддомен) требует пересмотреть модель CSRF.

Локально модель та же: портал и админка — HTTPS на `<LOCAL_DOMAIN>` и `admin.<LOCAL_DOMAIN>` (поддомены `duckdns.org`), куки, same-site и `Sec-Fetch-Site` проверяются как в проде ([reverse-proxy](../system/reverse-proxy.md)).
