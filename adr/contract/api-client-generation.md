# Клиент API на фронте

Область: frontend · Диаграммы: [c4/3-frontend](../c4/3-frontend.md) · Код: `frontend/packages/api` (`orval.config.ts`, `src/generated/`, mutator)

## Контекст

Типы, запросы, Query-хуки и Zod-схемы для двух групп API не должны писаться руками и расходиться с бэкендом. Изменения контракта должны быть видны на ревью, а сборка фронта не должна зависеть от запущенного бэкенда.

## Решение

- Клиент генерирует **Orval** из снапшотов OpenAPI (`pnpm api:fetch` + `pnpm api:generate`): типы, `queryOptions`, хуки, Zod. Обе группы лежат в одном пакете `@qgames/api`, mutator общий.
- **Коммитится сгенерированный код** `src/generated/`, снапшоты `openapi/*.json` в `.gitignore`. Контракт виден по диффу сгенерированного кода.
- Режим `tags-split`: файл на тег (теги латиницей).
- SSE-ручки исключены из генерации fetch/хуков, их Zod-схемы событий берутся из components.

## Рассмотренные варианты

| Вариант | Почему нет |
|---|---|
| `@hey-api/openapi-ts` | Версия 0.x, частые ломающие изменения |
| openapi-typescript + openapi-fetch | Хуки Query и Zod-схемы пришлось бы писать руками |
| Генерация клиента при каждой сборке с живого бэкенда | Сборка фронта зависела бы от запущенного бэкенда, изменения контракта не видны в диффе |
| Коммит снапшота OpenAPI | Конфликты при параллельной разработке; контракт и так виден по диффу сгенерированного кода |
| Orval в режиме `split` | Один большой файл ручек конфликтует при параллельной разработке |
| Сгенерированный Orval fetch/хук для SSE-ручки | Повисает на бесконечном потоке, имя совпадает с хуком слайса |
| Фиктивный `application/json` у SSE-ручки ради Zod | Документ врал бы о формате ответа |

## Последствия

- Конфликты в `src/generated/**` руками не сливаются: берётся любая сторона и перегенерируется.
- Известные ограничения генерации обходятся на фронте с комментариями (`frontend/CLAUDE.md` §5).
