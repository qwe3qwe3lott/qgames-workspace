# Раскладка репозиториев и воркспейс агентов

Область: система · Диаграммы: [c4/2-containers](../c4/2-containers.md) · Код: три репозитория в одной папке

## Контекст

У проекта два независимых стека, Kotlin/Gradle и TypeScript/pnpm, а фичи обычно затрагивают оба. Разработчик один, код пишет Claude Code под его контролем. Нужны место, где агент видит обе стороны фичи, и место для общей документации системы.

## Решение

- Три git-репозитория лежат рядом в одной родительской папке с фиксированными именами: `qgames-backend-monorepo`, `qgames-frontend-monorepo`, `qgames-workspace`. Все пути между ними относительные (`../qgames-frontend-monorepo`).
- **Бэкенд и фронтенд** — монорепозитории своих стеков. Правила написания кода для ИИ лежат в их `CLAUDE.md` (корневой — ядро, вложенные — правила областей рядом с кодом).
- **Воркспейс** — рабочее место фич, затрагивающих обе стороны, и **единое описание системы** (`adr/`: ADR, C4, ERD). Здесь же процесс задачи, агент `reviewer` и общий `BACKLOG.md`.
- Коммиты во всех репозиториях делает разработчик. Рабочая ветка — `master`.

## Рассмотренные варианты

| Вариант | Почему нет |
|---|---|
| Один монорепозиторий на оба стека | Разные инструменты сборки и CI; сессия, открытая в одном стеке, тащила бы в контекст чужие правила |
| Документация системы в каждом репозитории | Описание расползается и расходится, общей картины нет |

## Последствия

- Сессия, открытая в одном репозитории, читает архитектуру из `../qgames-workspace/adr`, поэтому раскладка папок обязательна.
- Документация обновляется отдельным коммитом в воркспейсе вместе с изменением кода.
