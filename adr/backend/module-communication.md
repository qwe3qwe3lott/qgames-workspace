# Связь между модулями бэкенда

Область: backend · Диаграммы: [c4/3-backend](../c4/3-backend.md), [erd/game](../erd/game.md) · Код: `backend/<m>/<m>-api`, `UserProfilePublisher`, `UserProfileListener`, `UserProfileTable`

## Контекст

Модуль `game` показывает ник и аватар игроков, а они принадлежат `user-auth`. При смене профиля открытые комнаты должны узнать об этом. Модули обязаны сохранять границы, чтобы их можно было вынести в сервис.

## Решение

- **Синхронно:** вызов бина через интерфейс из `<m>-api`. Чужие репозитории и сервисы не используются.
- **Чтение чужих данных:** join со своими таблицами через **публичное описание таблицы** в `<m>-api` (только нужные колонки, только чтение). Сейчас это `UserProfileTable` (`id`, `nickname`, `avatar` таблицы `user`).
- **Побочные эффекты — события модулей:** data class в `<m>-api`, публикуется в транзакции изменения, принимается `@TransactionalEventListener(AFTER_COMMIT)`. Если слушателю нужна БД, он работает в своей транзакции `REQUIRES_NEW`. Сейчас это `UserProfileChanged`: game рассылает `users-changed` в комнаты пользователя.
- **Реестра публикаций нет:** событие, не доставленное из-за падения процесса между коммитом и слушателем, теряется. Поэтому слушатели только рассылают уведомления и данные не копируют.

## Рассмотренные варианты

| Вариант | Почему нет |
|---|---|
| Реплика профилей в game (таблица-копия по событию с `version`) | В одной БД копия не нужна: лишние таблица, событие с версией и идемпотентный upsert |
| Реестр публикаций Spring Modulith (`event_publication`) | Нужен для доставки данных между процессами и повторов, а слушатели только рассылают уведомления |

## Последствия

- Профиль всегда актуален, синхронизировать нечего.
- При выносе game в отдельный сервис join придётся заменить репликой или вызовом.
- Если процесс упадёт, `users-changed` может потеряться. Клиенты получат свежий снапшот при переподключении.
