# Архитектура бэкенда

Область: backend · Диаграммы: [c4/3-backend](../c4/3-backend.md) · Код: `backend/settings.gradle.kts`, `backend/app/.../ModularityTest`

## Контекст

Нужны аккаунты игроков, админка и комнаты с партиями для нескольких игр, причём всё должно работать на VPS 1 ГБ. Разработчик один. Границы между областями должны оставаться явными, чтобы область при необходимости можно было вынести в отдельный сервис.

## Решение

- **Модульный монолит на Spring Modulith:** одно приложение `app` (один процесс, порт 8080) из модулей `user-auth`, `admin-auth`, `game`. Модуль = реализация `<m>/<m>` + публичный контракт `<m>/<m>-api`. Связь между модулями — только через контракт и события ([module-communication](module-communication.md)).
- **Один модуль `game` на все игры:** комнаты и партии общие, правила игр подключаются модулями `games/*` ([game-rules-modules](game-rules-modules.md)).
- **`libs/common-*`** — общая инфраструктура без бизнес-логики (ошибки, веб, тесты).
- Границы проверяет Spring Modulith (`ModularityTest`). Пустые модули «на вырост» не заводятся.

## Рассмотренные варианты

| Вариант | Почему нет |
|---|---|
| Микросервисы (5 JVM: два gateway, user-auth, game, admin-auth) + Redpanda + Debezium | Не помещаются в VPS 1 ГБ (~3 ГБ в простое); межсервисные вызовы, прокси и CDC ради одного разработчика |
| Отдельный сервис на каждую игру | N баз, образов и деплоев при одинаковой инфраструктуре пошаговых игр |
| Отдельный модуль game-lobby | Комнаты и партии тесно связаны (старт комнаты создаёт партию), понадобились бы вызовы и события между модулями |
| Без общих `libs` | Инфраструктурный код дублировался бы в каждом модуле |

## Последствия

- Один образ, один деплой, транзакции внутри процесса. Модуль можно вынести в сервис, не переписывая контракт.
- Масштабирование только вертикальное ([scaling](scaling.md)).
