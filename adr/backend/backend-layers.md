# Слои модуля и ошибки

Область: backend · Диаграммы: [c4/3-backend](../c4/3-backend.md) · Код: `backend/<m>/<m>/src/main/kotlin`, `backend/libs/common-exception`

## Контекст

Бизнес-логика не должна зависеть ни от формата хранения, ни от формата API, ни от HTTP. Код модулей должен быть единообразным, чтобы в нём было легко ориентироваться.

## Решение

- **Пакеты type-sliced:** сначала тип (`controller/`, `service/`, `repository/`, `table/`, `model/`, `mapper/`), потом фича.
- **Слои:** таблица Exposed (как в БД) → ручной `RowMapper` → **модель** (с ней работают сервисы) → `ResponseMapper` → DTO контракта (только в контроллерах). Составные ответы собирает сервис в композитную модель.
- **Репозиторий всегда двухслойный:** фасад `<Имя>Repository` (его видят сервисы) + `<Имя>ExposedRepository` (работа с хранилищем).
- **Ошибки:** `QgamesException` → `ClientException` (400 и подклассы 401/403/404/409/422/429) / `ServerException` (500, 503). Статус задаёт класс ошибки, модули `HttpStatus` не указывают. Бизнес-ошибки создаются в каталогах-фабриках `<Фича>Errors`, коды — часть контракта. Ответ — `ProblemDetail` с `code` ([api-contract](../contract/api-contract.md)).
- Нарушение уникального индекса даёт 409 `CONFLICT`. Если причина важна клиенту, сервис переводит его в доменный код по имени индекса (`UniqueViolations`).

## Рассмотренные варианты

| Вариант | Почему нет |
|---|---|
| Domain-sliced пакеты (`auth/controller/…`) | Выбран единый type-sliced вид |
| Строки таблиц (`ResultRow`) в сервисном слое | Сервисы зависят от формата хранения (строки вместо enum) |
| MapStruct для строки ↔ модель | kapt замедляет сборку, тонкости с data-классами Kotlin |
| Двухслойный репозиторий только при нескольких хранилищах | Разнобой между сервисами, сервисы зависят от технологии хранения |
| Сервисы возвращают DTO контрактов | Бизнес-логика зависит от формата API |
| Ассемблер ответа, который сам ходит в репозитории | Чтение данных смешано с маппингом |
| `ApiException(HttpStatus, …)` из сервисов | Сервисный слой знает про HTTP |
| Плоская иерархия ошибок | Нельзя одной веткой отличить ошибки клиента от ошибок сервера |
| Класс на каждую бизнес-ошибку | Десятки мелких классов без пользы |

## Последствия

- Больше файлов на фичу (таблица, модель, два маппера, два репозитория), зато каждый слой заменяем.
- Правила оформления (имена, `@Order` у своих advice, `noRollbackFor`) лежат в `backend/CLAUDE.md` §2.
