# Масштабирование: один инстанс

Область: backend · Диаграммы: [c4/3-backend](../c4/3-backend.md), [c4/deployment](../c4/deployment.md) · Код: `RoomStreamRegistry`, `SessionStreamRegistry`, `SessionStateCache`, джобы game

## Контекст

Прод — один VPS 1 ГБ. Поддержка нескольких инстансов (распределённые блокировки, общий кеш, ShedLock, sticky-сессии для SSE) усложнила бы код без нужды.

## Решение

- **Одно приложение, один инстанс.** Несколько инстансов app не поддерживаются.
- В памяти процесса допустимы только реестры открытых SSE-потоков (привязаны к соединениям) и кеш состояний партий (только ускоряет сборку, источник правды — журнал).
- Счётчики, лимиты, блокировки, присутствие хранятся в БД: атомарные `UPDATE … WHERE`, `SELECT … FOR UPDATE`, аренды подключений. `SKIP LOCKED` и ShedLock не нужны.
- Джобы (`@Scheduled`) выбирают id без блокировки, затем обрабатывают каждую комнату в своей транзакции под её блокировкой с перепроверкой. У каждого джоба свой флаг включения, в тестах джобы выключены и вызываются напрямую.

## Последствия

- Простой код, нет распределённых проблем.
- Перезапуск процесса рвёт все SSE-потоки (клиенты переподключаются). Протухшие подключения убирает `RoomConnectionCleanupJob`.
- Второй инстанс потребует пересмотреть реестры, кеш и джобы — это архитектурное решение.
