# Тесты бэкенда

Область: backend · Код: `backend/app/src/test`, `backend/libs/common-test`, `backend/games/*/src/test`

## Контекст

Основные риски — в стыках: Security и куки, транзакции и блокировки, SQL через Exposed, события и SSE. Моки слоёв эти ошибки не ловят.

## Решение

- Тесты **максимально интеграционные**: MockMvc в настоящие контроллеры на полном контексте (все модули, настоящие цепочки Security), реальная PostgreSQL через Testcontainers (singleton), внешние HTTP-системы — через WireMock.
- Все интеграционные тесты лежат в `app`. Чистые тесты правил игр — в модулях `games/*`.
- Один `BaseIntegrationTest` со всеми `@MockkSpyBean`, поэтому контекст Spring один на прогон.
- Тестовые данные — `init/<модуль>.sql` через `@Sql` перед каждым тестом (TRUNCATE + фикстуры с фиксированными UUID), константы фикстур — в `TestData`.
- Предпочитаются параметризованные сценарные тесты. Состояние проверяется в БД через Exposed DSL.

## Рассмотренные варианты

| Вариант | Почему нет |
|---|---|
| init-скрипты только с очисткой, без фикстур | Тесты создавали бы данные через API — медленнее и шумнее |
| Программная очистка БД из кода теста | Состояние не видно из ресурсов |

## Последствия

- Для `./gradlew build` нужен Docker.
- Поведение, требующее второго контекста Spring (например, `API_DOCS_ENABLED=false`), автотестом не покрыто и проверяется вручную.
