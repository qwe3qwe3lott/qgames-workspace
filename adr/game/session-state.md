# Хранение и изменение состояния партии

Область: backend · Диаграммы: [c4/3-backend-game](../c4/3-backend-game.md), [c4/dynamic/move](../c4/dynamic/move.md), [erd/game](../erd/game.md) · Код: `SessionJournalService`, `SessionStateService`, `MoveTimeoutJob`

## Контекст

Партии разных игр должны храниться в общих таблицах, транслироваться зрителям по событиям (у каждого своя проекция со скрытыми данными), переигрываться и восстанавливаться. Ходы конкурируют с таймаутами и паузой.

## Решение

- **Состояние не хранится — это свёртка журнала событий** `room_session_event`. Журнал только дописывается, у каждого события свой seq. Формат событий — [session-events-format](session-events-format.md).
- Любое изменение партии идёт через `SessionJournalService` под **блокировкой комнаты**: состояние на `last_seq` → `GameRules.decide` → события в журнал → `pg_notify`.
- Ход проверяется **по текущему состоянию без версии**: недопустимый ход — 422 `MOVE_REJECTED` с `reason`. Мутации партии отвечают **204**, результат приходит потоком.
- Свёртки кешируются в `SessionStateCache` по `(sessionId, viewerKey) → (seq, state)`, дочитываются только новые события.
- **Таймауты** обрабатывает `MoveTimeoutJob` раз в секунду по проекции `move_deadline`. Блокировка — сначала комната. Что происходит при таймауте, решает игра (`onTimeout`). Ход, пришедший после дедлайна, но раньше джоба, принимается.
- Настройки игры хранятся JSON-ом в общих таблицах, поэтому новой игре не нужны свои таблицы.

## Рассмотренные варианты

| Вариант | Почему нет |
|---|---|
| Отдельные таблицы на каждую игру | Каждая игра тащит свои миграции и репозитории в общий модуль |
| `GameRules.applyMove` → новое состояние, хранимый `room_session.state` + отдельный `view` | Нет событий для потока и повтора; маскировка состояния и событий расходилась бы |
| `version` партии + `expectedVersion` в ходе (409 `SESSION_CONFLICT`) | Событий много (личные, таймер), строгая сверка давала бы ложные конфликты |
| Ответы хода и действий — вся комната с `session.state` | Гонка с потоком: старый ответ перетирал новые события |
| Таймауты лениво при GET комнаты | GET меняет данные, и нечего публиковать в SSE |
| Джоб блокирует сначала партию, потом комнату | Порядок, обратный ходу, ведёт к дедлокам |
| Пропуск хода по таймауту силами движка | Не во всех играх ход можно пропустить |
| Отклонять ход после дедлайна до срабатывания джоба | Лишний код ошибки ради окна ~1 с |

## Последствия

- Партию можно переиграть по журналу (`created_at` событий позволяет повтор в реальном или ускоренном времени).
- Сборка состояния стоит CPU, его экономит кеш с лимитом под heap ([memory-budget](../system/memory-budget.md)).
- Фронт не может «угадать» результат хода, он ждёт событие ([frontend-game-logic](../frontend/frontend-game-logic.md)).
