# Формат событий партии

Область: backend, frontend · Диаграммы: [c4/3-backend-games](../c4/3-backend-games.md), [c4/dynamic/move](../c4/dynamic/move.md) · Код: `backend/games/game-core` (`SessionEvent`, `SessionPatch`), `frontend/packages/game-core` (`applySessionEvent`)

## Контекст

События партии должны строить состояние на сервере и на фронте, маскироваться для разных зрителей, переигрываться и не требовать правок фронта при каждой новой игре.

## Решение

- Событие — **патч документа** `{status, meta, state}`: `method` (`PUT`, `PATCH`, `DELETE`, `INFO`) + `path` + `value` и говорящий `code` только для журнала.
- **Один общий применитель** на сервере (`SessionPatch`) и на фронте (`applySessionEvent`) с одинаковой семантикой. Своих редьюсеров у игр нет.
- Путь — сегменты: строка — ключ, `{id}` — элемент массива по id. Коллекции хранятся массивами объектов с `id`.
- `PATCH` — неглубокое слияние, `null` — это значение. Одно событие — одна операция.
- Первое событие — `session-started` = `PUT []` с начальным документом. Перед концом и отменой часы переходят в `STOPPED`.
- Пауза — статус таймера (`game-paused`/`game-resumed`), а не партии. `moveOptions` лежат внутри объекта игрока.

## Рассмотренные варианты

| Вариант | Почему нет |
|---|---|
| Типизированные события (`started`, `turns-changed`, `moved`…) + `evolve` у каждой игры, редьюсер на каждый тип на фронте | Каждый новый код игры требует правок на обеих сторонах |
| Пауза на уровне сессии (`session-paused`, статус `PAUSED`) | В играх без таймера пауз нет |
| JSON Pointer с индексами массивов (RFC 6902) | Индексы хрупкие: сдвиг массива — и маскированный клиент расходится с сервером |
| Коллекции как объекты по id (`players: {u1: …}`) | Меняется форма состояния, порядок живёт отдельно |
| Список операций в одном событии (`ops: [...]`) | Грубее детализация кодов |
| Глубокое слияние PATCH (RFC 7386, `null` удаляет) | Конфликтует с nullable-полями, дублирует DELETE |
| Событие без метода для информационных кодов | Неявный контракт |
| Таймер `RUNNING` после конца партии | Финальное состояние не самодостаточно для повтора |
| Начальное состояние функцией вне журнала | Скрытые данные пришлось бы маскировать в самом состоянии — тот же отдельный view |
| `moveOptions` списком на верхнем уровне состояния | В полном состоянии варианты разных игроков смешались бы |

## Последствия

- Новая игра не меняет ни контракт событий, ни фронтовый применитель. Новые коды дописываются только в описание (`SessionEventCodes.DESCRIPTION`).
- `value` в OpenAPI не типизирован, поэтому корректность состояния на фронте проверяют guard'ы ([frontend-game-logic](../frontend/frontend-game-logic.md)).
