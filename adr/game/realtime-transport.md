# Транспорт real-time событий

Область: backend, frontend · Диаграммы: [c4/dynamic/room-stream](../c4/dynamic/room-stream.md), [c4/dynamic/move](../c4/dynamic/move.md) · Код: `PgNotifier`, `RoomEventListener`, `SseWriter`, `frontend/apps/portal/src/shared/lib/sse`

## Контекст

Игры пошаговые: клиент редко шлёт действия и часто получает события (ходы, таймер, участники). События нужно доставлять быстро, в порядке коммитов, без потерь и без нагрузки на БД, растущей с числом зрителей.

## Решение

- **REST для действий + SSE для событий.** Два потока: комнаты (`/api/rooms/{id}/events`) и партии (`…/sessions/{sessionId}/events`).
- **Рассылка потокам — Postgres `LISTEN/NOTIFY`** (каналы `room_events`, `session_events`). `pg_notify` вызывается в транзакции изменения, Postgres доставляет уведомление после коммита и в порядке коммитов, поэтому outbox не нужен. В уведомлении только сигнал, данные диспетчер читает сам.
- `RoomEventListener` держит отдельное соединение вне пула. При обрыве он переподключается и закрывает все потоки, клиенты получают свежий снапшот.
- JWT проверяется только при подписке. Ping раз в 5 с.
- **WebSocket** — только для будущих игр с real-time перемещением игроков.

## Рассмотренные варианты

| Вариант | Почему нет |
|---|---|
| WebSocket для Каркассона | Для пошаговой игры избыточно |
| Короткий поллинг событий по `afterSeq` (в том числе каждым потоком из журнала) | Задержка до интервала опроса, нагрузка на БД растёт с числом зрителей |
| Внутрипроцессная шина событий (публикация в транзакции, номер по порядку коммитов) | Порядок коммитов пришлось бы воспроизводить самим; NOTIFY даёт его даром |
| Long polling | Ожидающим запросам всё равно нужна рассылка: сложность как у SSE без его преимуществ |
| Опрос комнаты во время партии, состояние партии в ответе комнаты | Задержка; ответы мутаций перетирали кеш без сверки |

## Последствия

- Proxy должен не буферизовать SSE и держать соединение дольше ping ([reverse-proxy](../system/reverse-proxy.md)).
- Работает только при одном инстансе (реестры потоков в памяти) — [scaling](../backend/scaling.md).
- Использует сырой SQL (`pg_notify`, `LISTEN`) — единственное исключение из [data-access](../backend/data-access.md).
