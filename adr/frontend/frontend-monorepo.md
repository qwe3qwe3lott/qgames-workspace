# Монорепозиторий фронта

Область: frontend · Диаграммы: [c4/3-frontend](../c4/3-frontend.md) · Код: `frontend/pnpm-workspace.yaml`, `frontend/turbo.json`

## Контекст

Два приложения делят UI-кит, клиент API и игровые пакеты. Версии библиотек не должны расходиться, а вложенных дублей в `node_modules` быть не должно. Цепочка поставок npm — заметный риск.

## Решение

- **pnpm + Turborepo**, только Node.js (версия в `.nvmrc`).
- Все зависимости лежат в корневом `node_modules` (`nodeLinker: hoisted`). **Одна версия каждой библиотеки** — `catalog` в `pnpm-workspace.yaml` (`catalogMode: strict`), версии точные.
- Защита цепочки поставок не ослабляется: релизы моложе `minimumReleaseAge` не ставятся, install-скрипты запрещены, agent skills зависимостей выключены (`skills.dirs: []`: это инструкции агенту из стороннего пакета).
- **Dev-серверы (`pnpm dev`) — через `pnpm --parallel`, а не turbo.** На Windows turbo запускает задачи через npm-шим `pnpm.cmd`, и на Ctrl+C cmd.exe ждёт ответа на «Завершить выполнение пакетного файла?», так что turbo зависает при остановке. Кеш и граф задач dev-серверам не нужны.
- Внутренние пакеты `@qgames/*` не собираются, исходники транспилирует сборщик приложения. Пустые пакеты «на вырост» не заводятся.

## Рассмотренные варианты

| Вариант | Почему нет |
|---|---|
| npm workspaces | При конфликте версий кладёт пакеты во вложенные `node_modules`, нет каталога версий |
| Nx | Много собственной магии и конфигурации, для трёх приложений избыточно |
| pnpm без Turborepo | Нет кеша и графа задач |
| `pnpm dev` через `turbo run dev` | Зависает на Ctrl+C на Windows при pnpm из `npm -g` (см. выше) |

## Последствия

- Новая зависимость сначала добавляется в каталог, по согласованию.
- CLI-генераторы (shadcn) могут дописывать каталог, их дифф нужно проверять.
