# E2E-тесты

Область: frontend, backend · Диаграммы: [c4/3-frontend](../c4/3-frontend.md), [c4/3-backend-game](../c4/3-backend-game.md) · Код: `frontend/e2e/`, `frontend/**/*.test-ids.ts`, `backend/game/game/.../RoomController.kt`

## Контекст

Ручная приёмка через Playwright MCP после каждого изменения долгая и не повторяется. Нужны e2e-тесты, которые читаются как тест-кейсы (шаги и ОР), переживают перевод интерфейса и проверяют многопользовательские сценарии, в том числе партии на тысячи ходов, где важно, какие данные получает каждый игрок и зритель.

## Решение

- **Пакет `frontend/e2e`** (Playwright, только Chromium) рядом с приложениями, а не в `apps/` или `packages/`: он импортирует `*.test-ids.ts` приложений. Тесты идут против поднятых стендов (compose бэкенда и фронта), адреса меняются через env.
- **Селекторы — только `data-testid` и `data-*`.** У компонента рядом лежит `<компонент>.test-ids.ts` с `generateTestIds('Name', ['el'])` из `@qgames/ui/lib/test-ids` → `{root: 'Name', el: 'name__el'}`. Одинаковые элементы различаются `data-*` (`data-user-id`, `data-x`), не текстом.
- **Page Object Model:** `ComponentModel` (создание только через `Model.new(page)`), `PageModel` с `open(...)`. Локаторы строятся по testIds. В тестах нет `page.goto` и импортов моделей (ESLint): всё приходит фикстурами `testBasic` → `testPortal` / `testAdmin`.
- **Шаги и ОР:** `test.step('Шаг N: …')`, в каждом шаге — `testX.expected('…', checks)`, вложенный шаг `ОР: …` с проверками.
- **Вход — через API** тестовыми игроками профиля local; у воркера свой набор игроков. Несколько пользователей в тесте — фикстура `actors`: свой контекст браузера и модели на каждого.
- **Сценарии партий** — JSON: участники, seed, ходы и ожидаемые кадры потока партии для каждого участника. Ходы — только кликами по доске (драйвер на игру). Кадры записываются в браузере обёрткой `EventSource`, id и время заменяются подстановками. ОР пишет режим записи (`E2E_UPDATE_SCENARIOS=1`), человек проверяет дифф.
- **Seed** — заголовок `X-Qgames-Seed` ручки старта. Бэкенд учитывает его только при `seed-header-enabled` (профиль local), в контракт он не входит.

## Рассмотренные варианты

| Вариант                                      | Почему нет                                                             |
|----------------------------------------------|------------------------------------------------------------------------|
| Проект e2e в воркспейсе                      | Импорт test-ids через соседний репозиторий, дубли конфигов TS и ESLint |
| Селекторы по тексту и ролям                  | Будет перевод интерфейса                                               |
| Фикстуры `homePage2` на второй контекст      | Число фикстур растёт как «модели × контексты»                          |
| ОР в заголовке шага или в сообщении `expect` | Длинные заголовки; не видно, какие проверки относятся к ОР             |
| `webServer` Playwright + `pnpm dev`          | Прокси Rsbuild отличается от nginx прода                               |
| Ходы сценария через API                      | Пользователь хочет проверять и ввод хода в UI                          |
| Фиксированный seed всего стенда              | Один seed на все сценарии и ручную игру                                |
| Привязка ролей к игрокам на лету             | Не работает для игр со случайной раздачей                              |
| YAML или TS для сценариев                    | YAML — новая зависимость, TS на тысячах шагов тормозит тайпчек         |
| ОР сценария целиком руками                   | Тысячи кадров вручную не написать                                      |

## Последствия

- Тесты не ломаются от смены текстов и вёрстки, но каждый нужный тестам элемент требует test-ids.
- Записанный ОР фиксирует текущее поведение: ошибку, попавшую в запись, ловит только ревью диффа.
- Игроков на стенде 10, на воркер — 3: не больше 3 воркеров и 3 пользователей в тесте.

## Открытые вопросы

- Решить при сценариях на нестандартных правилах: настройки партии в файле сценария (BACKLOG «E2E: настройки партии в сценарии»).
