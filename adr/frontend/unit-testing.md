# Unit-тесты фронта

Область: frontend · Диаграммы: [c4/3-frontend](../c4/3-frontend.md) · Код: `frontend/packages/doc-patch`, `frontend/packages/game-core`, `frontend/apps/portal/src/**/*.test.ts`

## Контекст

На фронте лежит логика, которую ручная приёмка и e2e проверяют слабо: применитель патчей должен вести себя ровно как `DocumentPatch` бэкенда, guard'ы core и сверка seq решают, когда клиент переподключается. Расхождение даёт тихий рассинхрон у клиентов. UI-компоненты тестировать пока не нужно.

## Решение

- **Vitest** — unit-тесты чистой логики: применитель патчей, сверка seq, guard'ы и разбор документа партии, применение сообщений потока комнаты. Сложная логика тестируется, тривиальная — нет.
- Тесты лежат рядом с кодом (`*.test.ts`), конфиг Vitest не нужен. Пакет с тестами объявляет скрипт `test` (`vitest run`). Запуск — `pnpm test` (задача `test` Turborepo, без e2e).
- Сценарии применителя на фронте повторяют `DocumentPatchScenariosTest` бэкенда: меняется один — меняется другой.
- **UI-компоненты unit-тестами не покрываются.** Позже для них — скриншотные или снапшотные тесты.

## Рассмотренные варианты

| Вариант | Почему нет |
|---|---|
| Rstest (раннер команды Rspack/Rsbuild) | Моложе, экосистема меньше |
| Компонентные тесты (Testing Library) сейчас | Пользователь отложил UI до скриншотных или снапшотных тестов |
| Общий JSON сценариев применителя для бэкенда и фронта | Репозитории раздельные; сценарии дублируются руками |

## Последствия

- Вспомогательные данные тестов лежат в `src` пакета (`testData.ts`), в публичный `index.ts` не попадают.

## Открытые вопросы
